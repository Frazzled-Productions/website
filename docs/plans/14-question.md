## Decisions I took rather than referred up

**1. The major is 24.** The plan in PR #21 called this blocking on you. I disagree, and took it,
because #14 itself says "Which major to standardise on is your call, not mine", and every artefact in
the org points the same way: `poke-memory/.nvmrc` is 24 and enforced, and both the shared workflow's
own usage example and `frazzled-dotgithub/README.md` tell consumers to use 24. Node 20 left upstream
maintenance on 30 April 2026, so option B in the plan ("20, written down as deliberate") would have
been writing down an end-of-life major five months after the fact. Vercel's current default build
runtime is Node 24, and this repo had no `engines` and no `vercel.json`, so the live site was most
likely already building on 24 while CI validated 20. On that reading, pinning 24 does not change
production, it makes CI stop lying about it. The PR's preview deployment is where that gets
confirmed, before anything merges.

**2. Enforcement is a repo-local check, not a port of `poke-memory`'s.** The plan's option 2B
proposed copying that repo's ~145-line drift script and its own workflow. I wrote a shorter check
against the four things that actually exist here, and (once the blocked edit lands) it runs as one
step in the existing job rather than as a second workflow with its own checkout and setup. Same
forcing function, much less duplicated script, and no second copy of a file whose duplication is the
same single-source problem one level up.

**3. `@types/node` went `^20` to `^24`.** Not in the plan. It was a fourth statement of an intended
Node major sitting in this repo, describing a runtime we do not run, so leaving it at `^20` would
have recreated the exact defect #14 is about. `tsc --noEmit` passes on the new types.

## The open question

**`frazzled-dotgithub` is still self-contradictory, and fixing it is a shared-repo mutation.**
Its reusable workflow defaults `node-version` to `'20'` while its own header example and README
snippet both show `'24'`, so a consumer that copies the docs gets one answer and a consumer that
omits the input silently gets another. No repo consumes it today, so this is latent.

- **(A, recommended) File one issue there** covering both the default and the README, recommending
  the input lose its default entirely so a consumer must state its major rather than inherit a silent
  one. Cheap, keeps the artefact that is meant to settle the convention from being the thing that
  muddles it, and it is the org's issue-first process.
- **(B) Fold it into a single cross-repo change** now that the major is settled, updating the default
  to 24 and leaving the README alone.
- **(C) Leave it** until a repo actually consumes the workflow.

**Trade-off.** (A) and (B) reach nearly the same place; the difference is whether a consumer can
inherit a major without saying so. Dropping the default makes the choice explicit at every call site,
which is what stopped this repo from stating its own major in the first place. (B) is one fewer step
but keeps the silent-inheritance trapdoor open. (C) costs nothing today and is defensible while the
workflow has no consumers, but it leaves the wrong default in place for whoever first adopts it, and
adoption is exactly when nobody is reading the workflow's header comment. Filing or editing anything
in a shared repo is a GitHub state mutation, so this is a question rather than a filed issue.

**Secondary, lower stakes.** Should the drift check run as a step in the existing CI job (what the
blocked patch above does) or as its own workflow with path filters, the way `poke-memory` does it? I
prefer the step: this job is four commands long, the check takes milliseconds, and a separate
workflow is a second checkout for the same signal. Say if you would rather have parity with
`poke-memory` instead.
