# Plan: #14 Node major is unpinned here and hardcoded to '20' in CI

## What this is

Give this repo one file that states the required Node major, and make CI, Vercel and a human
cloning the repo all derive the answer from it. Today `'20'` appears once, inside a CI step
(`.github/workflows/ci.yml:21`), and nowhere else: there is no `.nvmrc` and no `engines` block in
`package.json:1-28`. I checked the history, and the literal arrived with the workflow itself
(`ff2c82b`, "Add CI workflow and typecheck script", 4 June 2026) with no rationale in the message or
the file, so the issue is right that nothing records whether 20 is deliberate.

I verified every cross-repo claim in the issue rather than taking it on trust:

| Claim | Verified |
| --- | --- |
| `poke-memory` pins and enforces 24 | `poke-memory/.nvmrc` = `24`; `poke-memory/package.json:5-7` `"node": "24.x"` with `preinstall`/`prebuild` guards; `poke-memory/.github/workflows/node-version-drift.yml` fails CI on any reintroduced `node-version:` literal |
| The shared workflow contradicts itself | `frazzled-dotgithub/.github/workflows/ci.yml:25` `default: '20'`, its own usage example at line 10 shows `'24'` |
| Next 16.2.7 tolerates 20 | `package-lock.json:5209-5211` records `"node": ">=20.9.0"` for `next` |

The mechanism below is identical whichever major is chosen. The number itself is a decision for
Fraser (question 1), and it is the only thing blocking implementation.

## Files to change

- **`.nvmrc`** (NEW, repo root) - one line, the chosen major (e.g. `24`). The single source of truth
  that `nvm`/`fnm`, CI and the drift check all read.
- **`package.json`** - add an `"engines": { "node": "<major>.x" }` block (natural home is after
  `"private": true` on line 4, matching `poke-memory/package.json:5-7`). Vercel reads this to choose
  the build runtime, and npm warns on a mismatch locally.
- **`package-lock.json`** - regenerated by `npm install`, not hand-edited: npm mirrors `engines` into
  the lockfile's root `packages[""]` entry (confirmed in `poke-memory/package-lock.json:58-60`). CI
  runs `npm ci`, so a stale lockfile would fail the build.
- **`.github/workflows/ci.yml:21`** - replace `node-version: '20'` with
  `node-version-file: .nvmrc`. Line 22's `cache: 'npm'` is unaffected, and `actions/setup-node@v4`
  (line 19) already supports `node-version-file`, so no action bump is needed for this change.
- **`README.md`** - state the required Node major in "Getting started" (lines 15-22), so someone
  cloning the repo learns it without opening a workflow file. This is also the file the drift check
  compares against under option B or C below.
- **`AGENTS.md`** - one line under "## Conventions" (lines 12-16) recording the chosen major and
  that `.nvmrc` is its home of record. This is the part that answers the issue's real complaint, that
  the next person cannot tell whether the current value is deliberate or drift.

Only if question 2 lands on option B or C, both NEW (this repo has no `scripts/` directory today):

- **`.github/workflows/node-version-drift.yml`** - adapted from `poke-memory`'s, path filters
  narrowed to the files that exist here.
- **`scripts/check-node-version-drift.mjs`** - adapted from
  `poke-memory/scripts/check-node-version-drift.mjs`. Drop its `AGENTS.md` `node@N` and Playwright
  image clauses, which have no counterpart here; keep the workflow-literal scan and the README prose
  scan.

Option C only:

- **`scripts/check-node-version.mjs`** plus `preinstall` and `prebuild` entries in `package.json`,
  ported from `poke-memory/scripts/check-node-version.mjs`.

Explicitly **not** in this repo, so not on this branch: `frazzled-dotgithub/.github/workflows/ci.yml:25`
and `frazzled-dotgithub/README.md:18` (the issue's suggested fix 2). See question 3.

## Approach

`.nvmrc` becomes the one statement of the required major; CI derives it via `node-version-file`, and
`engines` restates it for the two consumers that cannot read `.nvmrc` (Vercel's build image and npm's
own warning). Two files hold the number instead of one, which is a small cost, and it is the same
shape `poke-memory` already runs, so the org gets one answer rather than three.

Rejected:

- **Leave `'20'` and just document it.** Cheapest, and the issue concedes 20 is not broken. Rejected
  as the default because Node 20's upstream maintenance window has ended (see risks), so documenting
  it means writing down a decision with a short shelf life. Still available as option 1B below, since
  this is Fraser's call and not mine.
- **Make `package.json` the source of truth and point CI at it** (`node-version-file: package.json`,
  which setup-node can read from `engines`). Avoids the second file, but `.nvmrc` is what the version
  managers and `poke-memory` read, so `engines` alone would leave the laptop unmanaged and diverge
  from the sibling repo for no gain.
- **Adopt the shared reusable workflow** (`Frazzled-Productions/.github/.github/workflows/ci.yml@main`).
  Tempting, since it would settle the convention centrally, but it replaces this repo's whole CI file
  and inherits the disputed `'20'` default, which is the thing #14 is complaining about. Wrong order:
  fix the default there first, adopt later, separately.
- **Set the Node version in the Vercel project dashboard only.** Invisible to the repo and to CI,
  which is precisely the failure mode here.

## Testing

This repo has no test runner (`package.json:5-11` has no `test` script), so the build is the test.
Do not invent a test framework for this change.

1. **Local, under the chosen major.** `nvm install <major> && nvm use` (or put Homebrew
   `node@<major>/bin` on PATH), confirm `node --version`, then `npm ci`, `npm run lint`,
   `npm run typecheck`, `npm run build`. This machine's default is currently v26.3.0, so a run in the
   default shell proves nothing about the pinned major.
2. **CI on the PR.** The "Setup Node" step log must show the version resolved from `.nvmrc`, and
   lint, typecheck and build must pass on it. That is the primary evidence.
3. **The PR's Vercel preview deployment.** Its build log names the Node version it used. It must show
   the chosen major, which proves `engines` took effect over the project setting. If it shows a
   different major, `engines` did not apply and the project setting needs checking before this merges.
4. **Option B or C only, both directions.** Positive: the drift job passes on the branch as written.
   Negative: on a scratch commit, reintroduce `node-version: '20'` into `ci.yml`, push, confirm the
   job fails with the expected message, then revert. A check that has never failed is
   indistinguishable from a check that cannot fail.
5. **Option C only.** Run `npm install` in a shell on the wrong major and confirm it exits non-zero
   with the guard's message rather than proceeding.

## Risks and unknowns

- **The Vercel project's current Node version is not knowable from the repo.** There is no
  `vercel.json`, and the dashboard setting is not in git. If production currently builds on 20, the
  first deploy after this lands is the first production build on the new major. Step 3 above is what
  de-risks that, and it happens on the PR, before merge.
- **Node 20 is past its upstream maintenance window** (ended 30 April 2026 per the Node release
  schedule). I could not reach nodejs.org from this unattended session, so confirm that date before
  choosing option 1B. It is the main factual input to question 1.
- **`engines` value format matters to Vercel.** Use the major-selecting `"24.x"` form that
  `poke-memory/package.json:6` uses, not a loose range such as `">=24"`, which is less predictable in
  how the build image resolves it.
- **npm will not enforce `engines` on its own.** There is no `.npmrc` here, so without
  `engine-strict=true` a mismatch is a warning (`EBADENGINE`), not a failure. That is intended under
  options A and B; option C is what turns it into a hard stop.
- **Porting the drift script duplicates it.** A second ~145-line copy of a script in the org is the
  same single-source-of-truth problem one level up. The proper home is a shared action or workflow in
  `frazzled-dotgithub`, which is a bigger change than #14 and should not be smuggled into it.
- **A bare major in `.nvmrc` floats the patch version.** CI and the laptop can differ in patch. That
  is deliberate and matches `poke-memory`; the alternative is a full pin that needs bumping often.
- **No dependency blocks either candidate.** `next` requires `>=20.9.0` (`package-lock.json:5210`)
  and `eslint` ^9 is satisfied by any of 20, 22 or 24.

## Open questions for Fraser

**1 (blocking). Which major?**

- **(A, recommended) 24.** Matches `poke-memory/.nvmrc`, matches what both the shared workflow's own
  usage example (`frazzled-dotgithub/.github/workflows/ci.yml:10`) and its README snippet already
  tell consumers to use, and is Vercel's current default build runtime. One answer across the org,
  and the artefacts that disagree become a single wrong default to fix rather than a genuine split.
- **(B) 20, written down as deliberate.** Zero behaviour change, zero deploy risk, and the issue is
  satisfied purely by documentation. The cost is that it standardises on a major whose upstream
  support has ended, so the same decision comes back within months, and it leaves this repo as the
  only one in the org on 20.
- **(C) 22.** Supported and further from end of life than 20, but it matches nothing else in the org,
  so it buys a third answer to a question that currently has too many.

**Trade-off.** (A) costs one production build on a runtime this site has never been built on, which
the preview deploy exposes before merge, and this is a static marketing site with no server-side
dependencies to trip over. (B) is genuinely cheaper today and is a legitimate answer, per the issue's
own "if 20 is deliberate here, that is a fine answer", but it defers rather than settles. I recommend
24. Everything above is written so the number is a one-token substitution.

**2. How much enforcement?**

- **(A) Declaration only.** `.nvmrc`, `engines`, `node-version-file`, README and AGENTS lines. About
  twenty minutes, six files, nothing to maintain.
- **(B, recommended) Declaration plus the drift workflow.** Adds the two new files listed above so a
  reintroduced literal fails CI. This is what `ops/standards/conventions.md` asks for when it says
  every single-source helper ships with a forcing function, and it is a three-minute CI job with no
  `npm ci` step.
- **(C) Full `poke-memory` parity,** adding the `preinstall`/`prebuild` guard.

**Trade-off.** (A) leaves a convention-only rule, which the standard names as the thing that
fragments eventually, and this repo is exactly where it already fragmented. (C) is the strongest, but
it hard-fails `npm install` in a shell on the wrong major, and this machine's default Node is 26, so
every session in this repo would have to switch Node before installing anything. That friction is
worth it in `poke-memory`, where a wrong-Node build fails cryptically deep in the build; it is harder
to justify on a single-page marketing site. (B) catches the specific regression #14 is about, at the
cost of maintaining a duplicated script. Your call on whether the forcing function earns its keep
here.

**3. The `frazzled-dotgithub` half.** The issue's suggested fix 2 cannot be done from this branch, as
it is a different repo. I would file one issue there covering both the `default: '20'` on line 25 and
the README snippet, recommending the default be dropped entirely so a consumer must state its major
rather than inherit a silent one. That is a new issue in a shared repo, which your standing rule says
to ask about first, so: file it, or fold it into a single cross-repo change once question 1 is
settled?
